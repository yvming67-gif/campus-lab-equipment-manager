## PRV-01 资源分页混合不同查询条件

- 类型与证据：已确认缺陷；初始代码确认。一般：会把旧资源结果标为新时段，误导可预约判断，但最终提交仍由后端规则保护。
- 模块/角色：小程序资源目录，学生、教师。
- 初始位置：`miniprogram/controllers.js`，resources.load，初始约第 49—57 行；more 与 openResource。
- 条件与步骤：成功按日期 A、10:00—11:00 查询第 1 页且存在下一页；修改日期或起止时间但不点“查询”；点“加载更多”。load(page>1)直接读取当前编辑中的 slot，请求新时段第 2 页，同时保留旧时段第一页。
- 预期：下一页沿用已应用条件，或检测条件变化后从第一页重新查询；列表标签、每项 available 与进入详情携带的时段保持一致。
- 实际/根因：初始实现没有保存成功查询的完整条件签名；成功后把全局 `_appliedSlot` 和 `appliedTime` 改为新时段，但旧 items 未被替换。
- 最小建议：成功查询后保存条件；分页检测条件变化就重置为第 1 页，或冻结已应用条件并明确提示待应用。
- 验收：返回可区分 A/B 时段的模拟结果，验证变更后不会出现 A/B 混合，详情携带的是当前结果对应时段；同时验证倒序异步返回不能覆盖较新查询。
- 状态/关联：已报告主 agent；与 PRV-03 分别修复。

## PRV-02 个人统计与管理员列表范围不一致

- 类型/严重程度/证据：已确认缺陷；一般；初始代码确认。
- 模块/角色：网页工作台，兼任学生或教师的实验室管理员。
- 初始位置：`templates/dashboard.html:5`；`core/views.py` dashboard 的 mine 统计与 bookings 的 scoped_bookings。
- 后续发现的同根因实例：`templates/dashboard.html:6`，“接下来要使用”栏的“我的记录”入口同样未限定 scope=mine；已补充通知主 agent，不能只修三项统计入口而漏记此处。
- 条件与步骤：管理员本人有 1 项已确认预约，其管理实验室其他人还有若干已确认预约；点击“我的已确认”。
- 预期：显示本人统计对应的记录，数量和语义一致。
- 实际：初始链接仅 `?status=CONFIRMED`；scoped_bookings 对 LAB_ADMIN 返回本人及授权实验室其他人的记录。不是越权读取，但入口承诺与列表不符。
- 根因：个人范围没有成为链接和查询的显式过滤条件。
- 最小建议：加入 scope=mine 并在后端 filter(applicant=request.user)，表单与分页保留范围。
- 验收：本人和他人各一记录，点击三类个人入口后仅本人；普通管理列表仍按原授权范围。
- 状态：已报告主 agent；修正待独立复核。

## PRV-03 临时导航缓存与空字符串混淆

- 类型/严重程度/证据：已确认缺陷；轻微；初始代码确认，微信 API 缺失缓存值与旧测试 mock 的差异需在回归中保留。
- 模块/角色：小程序预约列表，学生、教师。
- 初始位置：`miniprogram/controllers.js` bookings.onShow，初始第 135—138 行。
- 步骤：在预约列表选择“已取消”，进入详情再返回；此时并无工作台临时筛选缓存。微信 getStorageSync 对缺失键可返回空字符串，初始实现将所有 string 识别为待消费筛选，因而重置成“全部”。
- 预期：只有确实存在的工作台导航指令覆盖当前筛选，普通返回保持用户选择。
- 根因：用空字符串同时表示“全部筛选指令”和“缓存不存在”；旧单测 Map mock 返回 undefined，漏掉平台差异。
- 建议：存结构化对象 `{status: ...}`，仅消费有效对象；补空字符串返回值单测。
- 验收：工作台状态跳转有效；无缓存时反复 onShow 保持原 statusIndex。
- 状态：已报告主 agent；修正待独立复核。

## PRV-04 待验收筛选隐藏本人维修记录

- 类型/严重程度/证据：已确认缺陷；一般；初始代码确认。
- 模块/角色：网页维修任务，维修人员及兼任管理员的维修人员。
- 初始位置：`core/views.py` work_list，初始第 268—272 行；`templates/work.html:1` 新增“待独立验收”状态入口。
- 条件与步骤：维修人员有本人指派且已提交的 AWAITING_ACCEPTANCE 工单；打开维修任务的“待独立验收”。
- 预期：维修人员可以查看本人已提交待验收记录及后续进展；不得办理自己的验收。管理员用于办理验收的专门队列才排除本人执行的任务。
- 实际：无条件 `qs.exclude(assigned_to=request.user)`，纯 TECHNICIAN 的 scoped_work 仅含本人任务，被全部排除。既有后端独立验收条件正确，错误发生于新增列表过滤。
- 根因：把“可由我办理验收”当成所有角色的“待验收状态查询”。
- 建议：分离 state filter 和 actionable queue；普通状态查询保留有权查看的任务，办理队列额外限定管理员授权范围并排除本人。
- 验收：维修人员能看到本人待验收任务；本人验收仍拒绝；管理员办理队列计数和列表相同。
- 状态/关联：已报告主 agent；与 PRV-06 同样涉及计数/列表，但根因与入口不同。

## PRV-05 待复核队列包含不能自行复核的本人预约

- 类型/严重程度/证据：已确认缺陷；一般；初始代码确认。
- 模块/角色：网页工作台、预约工作队列，LAB_ADMIN + STUDENT/TEACHER 多角色用户。
- 初始位置：`core/workbench.py` booking_queue 的 recheck、tasks_for；`core/views.py` bookings 的 queue 分支；依据 `core/coordination.py:67` 禁止本人复核。
- 条件与步骤：管理员本人预约了自己授权实验室的资源，预约 CONFIRMED 且 review_required=True；打开工作台“待复核承诺”。
- 预期：可办理工作队列只列本人具备范围且能合法执行的事项；本人预约仍能从个人记录查看并联系其他管理员。
- 实际：只有 review 队列排除本人，recheck 未排除，所以待复核计数及列表含不能办理的本人预约。尝试复核将被服务层拒绝，没有实际越权。
- 根因：队列未复用独立复核执行者约束。
- 建议：recheck 计数与队列同步 exclude(applicant=user)，保留个人记录及说明。
- 验收：本人待复核预约不出现在可办理队列，他人且本实验室的待复核预约出现；未授权实验室不出现。
- 状态：已报告主 agent；修正待独立复核。

## PRV-06 异常办理计数与打开列表范围不同

- 类型/严重程度/证据：已确认缺陷；一般；初始代码确认。
- 模块/角色：网页工作台“异常待核实”，多角色实验室管理员。
- 初始位置：`core/workbench.py` tasks_for pending 卡；`core/views.py:41` scoped_incidents 与 incidents。
- 条件与步骤：管理员对实验室 A 有管理范围，同时因学生/教师身份报告或借用实验室 B 资源，B 异常 PENDING；A 无待核实异常。工作台显示 0，点击后可能看到 B 的异常。
- 预期：工作队列显示同一组可办理记录，不应将有权查看但无权核实的记录混入办理集合。
- 实际：卡片计数额外限定 `resource__lab__labgrant__user=user`，链接只有 status=PENDING。scoped_incidents 是本人报告、本人预约、维修指派和管理范围的并集，因此列表集合更大。
- 根因：链接没有携带“授权实验室内可办理”的范围语义。
- 建议：新增仅用于办理的明确队列参数，后端同步管理角色、实验室范围和状态过滤，普通异常列表保留原可见范围。
- 验收：构造 A/B 两组异常；卡片数与目标列表一一对应，普通列表仍可见本人 B 报告但不可核实。
- 状态：已报告主 agent；修正待独立复核。

## PRV-07 办理队列缺少范围提示和退出操作

- 类型/严重程度/证据：优化建议；轻微；代码确认。不是权限绕过，问题是列表当前额外过滤条件不可见，容易误解数据遗漏。
- 模块/角色：网页异常追踪、维修任务；实验室管理员及多角色用户。
- 位置：`templates/incidents.html:1`、`templates/work.html:1`；新引入的 queue=managed、queue=acceptance 处理入口。
- 条件与步骤：从工作台办理卡片进入，列表只显示状态标签，没有说明当前还限定“管理范围”“可由我独立验收”；再点击同名状态标签，链接又只保留 status，范围隐式变化。
- 预期依据：界面应解释当前筛选条件；与预约队列已有范围说明保持一致。这是可用性建议，不是新增学校制度。
- 实际/根因：模板没有渲染 queue 上下文，状态链接不携带 queue，也未明确说明它们将退出办理队列。
- 最小建议：加入队列范围说明与“查看全部有权记录”链接，让用户区分“可以查看”和“由我办理”；状态入口的范围变化文案明确。
- 验收：从卡片进入能看到范围说明，明确退出后看到完整有权列表；后端范围与权限保持不变。
- 状态/关联：已通知主 agent；关联 PRV-04、PRV-06，但这是独立的界面解释问题。

## PRV-08 培训资格名称不是稳定唯一列表键

- 类型/严重程度/证据：待验证风险；轻微；模型、API 与 WXML 代码确认存在重复键条件，微信运行时的具体错行表现尚未复现。
- 模块/角色：小程序个人页；持有多个资格的学生、教师。
- 位置：`core/models.py:56` QualificationType.name 无唯一约束；初始 `core/miniapi.py:235` 仅序列化名称；`miniprogram/pages/profile/index.wxml:1` 使用 wx:key="name"。
- 条件与步骤：两个资格类型有不同唯一编号但名称相同，同一用户持有两项；打开培训资格列表，更新其中一项有效性后刷新。
- 预期依据：动态列表应使用稳定且唯一的业务编号或主键，名称允许重复不能当作唯一标识。
- 实际：合法数据可令两个 wx:for 项使用相同 key。是否错用行节点、显示旧状态仍待微信容器验证，不能写成已观察事实。
- 根因：API 遗漏资格类型唯一标识，客户端选择非唯一 name。
- 建议：序列化 qualification.code 或 id，并用该字段作为 wx:key；保留 name 兼容原名称显示。
- 验收：构造同名异编号两资格，接口返回可区分的唯一值；WXML 使用唯一字段；编译通过；真机行复用问题仅在实际执行后判定。
- 状态：已通知主 agent，等待最终代码复核；未宣称有隐私泄漏或后端资格绕过。

## PRV-09 历史维修参与者仍进入本人独立验收队列

- 类型/严重程度/证据：已确认缺陷；一般；代码确认。服务层最终拒绝，因此不是验收越权，但工作台可办理事项计数和承诺不准确。
- 模块/角色：网页工作台与维修验收办理队列；曾参与维修、后来转为其他负责人或兼任管理员的人。
- 位置：`core/workbench.py` tasks_for 的 acceptance 过滤；`core/views.py` work_list 的 queue=acceptance；依据 `core/services.py:467`—`472` accept_work 的 AuditEvent 历史参与检查。
- 条件与步骤：管理员兼维修人员曾对工单执行 START、PROGRESS 或 SUBMIT；工单重新指派给另一维修人员，最终状态 AWAITING_ACCEPTANCE；原参与者打开“维修待验收”卡片。
- 预期：普通状态列表仍可查看有权记录，标为“可由我独立验收”的办理队列应排除当前和历史维修参与者。
- 实际：初始新队列只排除 assigned_to=user，未排除 AuditEvent 中历史参与，最终办理会被 accept_work 拒绝。
- 根因：工作台抽取的资格集合与既有服务层独立验收条件不完全一致。
- 最小建议：用共同 helper 生成验收办理 queryset，排除当前执行者及维修审计 START/PROGRESS/SUBMIT 中 actor=user 的工单，卡片和列表共同使用；保留最终服务检查应对并发变动。
- 验收：历史参与后重新指派的工单在普通可见列表中保留，但不出现在原参与者验收队列；另一位授权且无维修参与的管理员能看到；提交时原参与者仍拒绝。
- 状态/关联：已通知主 agent；PRV-04 解决普通状态可见性，PRV-09 解决可办理集合完整性，两者不可相互替代。
