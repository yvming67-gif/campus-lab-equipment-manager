## 对比结论：采用什么、暂不采用什么

1. **采用层级明确的资源目录。** 事实依据是多个高校/平台公开区分设施、设备或可预约房间；推论是本课程演示需要展示多个管理单元并为每个管理单元设置多个房间。当前种子新装数据为3个管理单元、6间场地、9项设备，其中每个管理单元有2间场地；另用一个固定设备和一个维护中场地演示关联约束与服务状态。这些均为标注的模拟课程数据，不是目标学校统计。种子命令只创建缺失的演示记录，不覆盖用户已有记录。
2. **开放日历按空间范围分层。** MRBS把具体房间作为预约对象；项目据此推论同一管理单元内的房间可能需要不同开放时段。因此采用管理单元默认周历、单间场地周历覆盖、管理单元单日例外优先的规则，并允许单间场地设置每周全天关闭。示例时段只是模拟值，真实开放日历须由学校责任岗位提供。
3. **不把已预约、已批准、已入场和实际离场合并。** 这是本项目既定业务规则，也与研究设施将预约、资格和实际访问分别说明的案例做法相容。现有数据库中的 Lab—Resource 关系已能支持一实验室多资源，不需为视觉效果改动该关系。
4. **安全信息使用有来源的版本记录。** 案例只支持“培训/规程需要与风险和责任相连”的一般设计方向，不能替代本校安全部门批准。故每个房间默认显示待确认；只有具备有效来源、版本、生效与复核日期且由不同授权管理员复核的版本才展示为已发布。
5. **暂不引入计费、复杂成本分摊、候补或信用处罚。** 这些能力在部分科研设施产品中可能存在，但不属于已经确认的课程规则；没有制度依据时不实现。
6. **公开案例没有证明其所有做法都适合本项目。** 例如科研仪器平台可能要求额外培训或由设施人员审批，而本项目已确认普通设备满足规则后自动确认、受限设备与场地由实验室管理员审批；本项目保留这一既定约束。

### 对“案例系统有什么缺点”的证据结论

本次查阅的官方说明主要描述服务范围、预约步骤、权限或培训安排，没有足够证据评价各产品的真实缺陷、用户抱怨、性能故障、使用成本或培训负担。因此不对MRBS、iLab、Stanford或高校平台贴上“难用”“流程复杂”等缺点标签。可以确认的是，它们服务于会议室、科研共享设施、样品制备或教学计算机房等不同场景，功能范围也不同；把科研平台的组权限、计费、设备培训或学期排期直接引入本项目，会增加规则维护和数据治理成本，但这是本项目的设计权衡推断，不是这些案例的已证实产品缺陷。优化顺序应由目标实验教学中心的真实制度和使用频次决定。
