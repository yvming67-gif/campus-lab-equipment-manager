## 4. 发现、整改与复验明细

### AUD-0045 固定设备与场地交接忽略对方超时实际占用

- 类型与严重程度：已确认缺陷；严重。管理员可能将仍被占用的教学空间交给下一位使用人，影响现场责任和安全安排。
- 证据状态：运行验证；影响设备借出、场地入场，涉及申请人和实验室管理员。
- 发现位置：`core/coordination.py:28` 的 `check_dependency`；`core/services.py:225` 的 `_check_start`。行号对应复验工作树，摘要见证据收据。
- 触发与复现：把设备设为固定设备并关联同实验室场地；按I-04建立相邻预约，前一设备借出不归还，在后一场地开始后5分钟执行入场。反方向使用I-06。
- 预期依据：既有固定设备/场地冲突规则与现场交接必须核实实际占用的业务目标；课程默认同一申请人的共同使用可排除本人。
- 原实际行为与证据：I-04未抛出业务拒绝，场地入场成功；原始 `first-run.log` 的断言失败保留于独立工作证据中。
- 根因：只比较预约计划时间区间，未检查未结束的Loan或RoomUse。
- 最小整改与实际结果：交接时启用实际占用检查，固定设备与依赖场地双向检查未结束事实；不伪造归还或离场时间。I-04、I-06最终均拒绝不应发生的交接。
- 验收与状态：同一原始断言和反向断言均通过，已修复并独立复验；关联AUD-0022、AUD-0007。

### AUD-0046 原领取宽限内无法完成受影响预约复核

- 类型与严重程度：已确认缺陷；一般。业务本来允许的宽限内交接因复核入口拒绝而中断。
- 证据状态：运行验证；预约复核，涉及申请人、实验室管理员。
- 发现位置：`core/coordination.py:65` 的 `recheck`，以及 `core/services.py` 的 `validate`、`validate_time`。
- 触发与复现：I-02。原预约尚未到领取截止，但安全分级变化已设置复核标记。
- 预期依据：已确认预约的领取宽限规则；复核只重核当前条件，不应将原预约视为在过去新建预约。
- 原实际行为与证据：10:05复核调用新建预约时间校验，抛出BusinessError；未完成复核。首次错误堆栈及异常类别已保留。
- 根因：复核完整复用新预约的“开始时间必须不早于现在”条件。
- 最小整改与实际结果：先验证原领取截止与原结束时间；当前身份、资格、状态仍按当前时间判断，时间窗核验使用原开始参照；原预约起止时间不变。
- 验收与状态：10:05复核、10:06领取通过，已修复并独立复验；关联AUD-0002、AUD-0043。超出领取截止的其它边界由主回归检查负责，不计作本次独立执行场景。

### AUD-0047 预约终止后仍保留当前待复核标记

- 类型与严重程度：已确认缺陷；轻微。状态说明相互矛盾，可能使申请人误以为已取消预约仍等待恢复。
- 证据状态：运行验证及代码确认；预约取消、协调取消、失效及维护取消，涉及申请人和管理员。
- 发现位置：`core/services.py:60` 的 `finish_booking`及各终态调用点；`core/coordination.py` 的复核拒绝、协调取消；`templates/booking.html:1`、`core/miniapi.py:164` 的状态展示。
- 触发与复现：I-07。先触发待复核，再取消预约。
- 预期依据：复核标记表示当前办理限制；终态应结束当前限制，历史通过审计与复核记录保留。
- 原实际行为与证据：取消后数据库仍有 `review_required=True`；页面和小程序说明据此继续显示待复核。第二轮失败记录保留。
- 根因：多条终态转换只保存status与reason，未同步结束当前复核标记。
- 最小整改与实际结果：终态统一清理当前复核标记及原因，同时追加结束记录；页面对非未结束预约作防御性显示处理，不删除原历史。
- 验收与状态：取消后状态为CANCELLED、标记False、原因清空，最终通过；其它终态入口为代码确认及主回归覆盖，已修复并独立复验该取消实例。关联AUD-0044、AUD-0046。

### AUD-0048 维修验收结案后异常仍宣称当前阻断服务

- 类型与严重程度：已确认缺陷；轻微。资源正常与异常详情“本异常阻断服务”并存，影响管理员判断。
- 证据状态：运行验证及模板代码确认；维修验收与异常详情，涉及维修人员、管理员和借用人。
- 发现位置：`core/services.py:459` 的 `accept_work`、`templates/incident.html:1`。
- 触发与复现：I-08，完整执行报告—确认—工单—维修提交—管理员验收通过。
- 预期依据：结案后当前阻断状态应与资源恢复一致；历史故障事实与原阻断原因继续保留。
- 原实际行为与证据：Incident为RESOLVED、Resource为NORMAL，但 `blocks_service=True`；第二轮断言失败。由于状态过滤，未观察到其继续实际阻止预约，影响主要是状态与界面说明。
- 根因：手工核实处置会清阻断标记，维修自动结案分支未执行对应更新。
- 最小整改与实际结果：维修结案同步设为False，审计保存原、新阻断标记。
- 验收与状态：完整维修闭环后RESOLVED/NORMAL/False三项一致，已修复并独立复验；关联AUD-0024。

上述四项均保留原发现，未因修复而从问题统计中删除。本独立发现集合为4项已确认缺陷：严重1、一般1、轻微2，当前均为已修复并复验。项目总台账还包含原43项及AUD-0044，合计48项；其完整分类、严重程度和状态统计以[问题整改台账](问题整改台账.md)为准，不将独立集合统计替代项目总统计。

## 5. 判断更正记录

最初阅读 `check_dependency` 时，曾怀疑两个不同Resource仅分别加锁，可能使固定设备与场地并发申请同时确认。进一步检查 `core/services.py` 的 `_locked_user_resource` 后确认，`select_for_update(no_key=True).select_related('lab')` 未限制 `of`，在该PostgreSQL查询中也锁住关联Lab；同实验室的流程因此串行。I-05的两线程实测最终只有一个确认。

最终结论：该“不同资源无共享锁”的初始怀疑被证伪，不登记成确定缺陷。本说明保留更正历史。测试只证明当前检查到的锁与一次双线程场景，不证明所有并发和未来改造都正确。后续若为提高并发而缩小锁范围，必须继续保护场地与固定设备依赖，不能只保留同Resource的时间排他约束。
