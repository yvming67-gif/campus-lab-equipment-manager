# 系统用例规约

版本2.3。业务来源与教学描述依据分别登记。UC-01、UC-23是共同支撑能力，不能解释为组织对外业务价值。步骤数据契约只突出关键交换，不声称取代完整字段、流程及异常说明。

## UC-01 登录系统

编号版本：SPEC-01 / 2.3；跨业务支撑用例

目标：在不保存学校密码的前提下建立可授权的身份会话

主要执行者：学生、教师及各管理岗位；次要参与者：学校统一身份认证系统；演示为独立模拟身份提供方

涉众利益：用户关心身份和退出状态；学校身份提供方关心凭据不泄露；管理岗位关心后续权限由当前授权判定。

业务来源：BUC-01,BUC-04；改进步骤：TO-E01,TO-R01

触发：访问保护功能或主动登录

前置条件：可访问认证入口；身份映射由授权岗位维护。账号是否存在和有效是执行中的检查，不预先假定成功。

成功后置：建立具有到期时间的会话；记录登录主体及渠道；显示当前角色入口。

最低保证：认证失败不产生已登录会话；原业务记录不变。退出或会话失效不删除业务历史。

基本流程：

1. 用户请求访问受保护业务，系统建立认证请求。

2. 网页身份提供方返回绑定本次会话的断言；小程序提供一次性学校登录凭据，演示使用明确标识的模拟身份。

3. 系统核验真实性、时效、请求绑定及本地身份有效性。

4. 系统建立会话并保存登录事件，返回当前角色及入口。

备选流程：

2a 模拟模式：仅由独立模拟身份服务验证演示凭据，继续步骤3，不将其称为学校认证。

4a 多角色：显示并集入口；每次业务仍按角色及对象范围重新检查，用例结束。

异常及并发：

2b 身份适配器缺失或不可用：拒绝认证并提示渠道不可用，不退回模拟成功，用例结束。

3a 断言被改写、超时、回放、账号不存在/停用或角色失效：不创建会话，说明失败，用例结束。

4b 技术保存失败：不返回成功会话，允许重新认证。

输入字段：

|字段|含义|类型|条件|范围|来源|校验|隐私|
|---|---|---|---|---|---|---|---|
|身份凭据|提供方确认身份的材料；模拟与正式分开|一次性断言/代码或演示凭据|认证时|提供方协议；演示断言60秒|用户/学校提供方或独立演示服务|签名、时效、回放和身份映射；不保存学校密码|认证通道；日志不记录原凭据|
|会话绑定|把返回身份绑定本次认证请求|不可预测随机标识|网页认证时|单次有效|系统|请求/回调绑定并消费|仅认证过程，不公开|

步骤与关键数据：步骤2接收适用输入；步骤4形成或呈现“身份会话”。结构：主体编号＋当前角色范围＋会话到期时间＋认证渠道

规则执行位置：BR-01→步骤3；BR-30→步骤3；BR-46→步骤2

输出与凭据：建立具有到期时间的会话；记录登录主体及渠道；显示当前角色入口。

对象状态：User,UserRole,LabGrant,UserQualification,AuditEvent；参见后置及状态事件字典。

业务规则及权限：BR-01,BR-29,BR-30,BR-46；学生、教师及各管理岗位；本人及授权实验室记录

约束：不适用预约时间与数量校验；相关对象状态和权限按本规约执行。

质量与设计：QR-01,QR-03,QR-08,QR-04,QR-09；沿用Django/PostgreSQL与原生小程序；网页断言60秒、绑定会话并单次消费；小程序会话与网页隔离。正式提供方缺失拒绝认证。

验收：AC-01,AC-02,AC-63

来源与待确认：SRC-A01,SRC-D02,SRC-E01,SRC-A02；真实学校制度与岗位范围待确认；本规约表达已接受课程方案。

描述方法依据：SRC-A03,SRC-A04,SRC-A05；不证明学校实际制度。

## UC-02 查询实验室与设备

编号版本：SPEC-02 / 2.3；用户目标用例

目标：找到符合活动需要的设备或整间场地及其使用限制

主要执行者：学生、教师；次要参与者：无额外外部参与者；显示数据不授予源对象管理权

涉众利益：申请人关心类型、地点及限制是否清楚；管理员关心档案由负责岗位维护，目录可见不等于获准使用。

业务来源：BUC-01,BUC-04；改进步骤：TO-E01,TO-R01

触发：打开资源目录或输入筛选条件

前置条件：受保护目录请求需有效身份；无须先选定存在的资源。

成功后置：返回分页目录及有权查看的资源详情；不形成预约承诺。

最低保证：查询失败不改变资源、预约或权限；不暴露他人申请内容。

基本流程：

1. 用户提出名称、编号、实验室或资源类型条件。

2. 系统解析条件，按稳定顺序读取集中档案并分页。

3. 系统展示编号、地点、类型、服务状态和审批要求。

4. 用户查看详情，系统补充配件/容量、固定依赖及取放说明，提示可用时段另查。

备选流程：

2a 条件为空或没有匹配：返回默认分页或明确空结果，保留条件，用例结束。

4a 需要目标时段结论：转UC-03；目录状态不能作为占用承诺。

异常及并发：

2b 筛选格式非法：指出字段，不执行该查询，返回步骤1。

4b 资源编号不存在：返回404或不存在提示，不生成空资源，用例结束。

输入字段：

|字段|含义|类型|条件|范围|来源|校验|隐私|
|---|---|---|---|---|---|---|---|
|检索条件|目录搜索字段组|可选文本/标识/枚举|可选|名称/编号、实验室、设备/场地类型|用户|合法字段及对象编号；保留筛选|不包含他人申请条件|
|分页|可重复定位的列表页码|正整数|可选，默认1|网页常用30条；报表50条；小程序20条|用户/系统分页链接|稳定排序并保留筛选；不以页码绕过权限|沿用对象权限|
|资源编号|唯一设备或整间场地标识|业务标识|查询详情/预约/报告时|既有资源；类型由档案决定|目录或受控URL|存在、类型一致；设备标签不因普通编辑变更|资源公共业务属性，不含他人申请|

步骤与关键数据：步骤1接收适用输入；步骤3形成或呈现“资源目录结果”。结构：资源编号＋名称＋实验室＋类型＋服务状态＋审批要求＋分页信息

规则执行位置：BR-29→步骤2；BR-31→步骤3

输出与凭据：返回分页目录及有权查看的资源详情；不形成预约承诺。

对象状态：Lab,Resource,EquipmentDetail,RoomDetail,Accessory；参见后置及状态事件字典。

业务规则及权限：BR-01,BR-29,BR-31；学生、教师；本人及授权实验室记录

约束：不适用预约时间与数量校验；相关对象状态和权限按本规约执行。

质量与设计：QR-01,QR-03,QR-08；沿用Django/PostgreSQL与原生小程序；只读目录与详情；分页稳定，档案可见不代表具备申请资格。

验收：AC-03,AC-04

来源与待确认：SRC-A01,SRC-D02,SRC-E01,SRC-A02；真实学校制度与岗位范围待确认；本规约表达已接受课程方案。

描述方法依据：SRC-A03,SRC-A04,SRC-A05；不证明学校实际制度。

## UC-03 查询资源可用时段

编号版本：SPEC-03 / 2.3；用户目标用例

目标：区分指定时段的资源可申请性与本人实际申请资格

主要执行者：学生、教师；次要参与者：无额外外部参与者；显示数据不授予源对象管理权

涉众利益：申请人关心结论适用于哪个时段和本人条件；下一位使用者关心实际未结束使用不会被计划掩盖。

业务来源：BUC-01,BUC-04；改进步骤：TO-E01,TO-E02,TO-R01

触发：选择日期、开始与结束时间并发起查询

前置条件：用户具有有效会话；目标编号和时段可在执行时校验。

成功后置：返回有时间口径的可用结论、阻断原因及重新提交校验提示；不占用资源。

最低保证：不产生预约、审核或实际使用；不泄露占用者隐私。

基本流程：

1. 用户指定资源或目录筛选和目标起止时刻。

2. 系统解析时区、时间格式、先后、窗口、粒度与时长。

3. 系统检查资源存在、服务状态、有效开放日历及未结束逾期。

4. 系统核对半开区间承诺及固定设备/场地依赖；显示时段结论。

5. 系统明确此为资源时段结论，提醒提交时另核验本人资格和配额；不表示已取得使用资格。

备选流程：

4a 仅有待审核竞争：可申请但不保证优先权，继续步骤5。

4b 同一教师的配套场地和固定设备：按允许共同使用处理；可移动设备不依赖场地，继续步骤5。

异常及并发：

2a 格式、先后、窗口、粒度、跨日、时长或开放区间不符：给出具体原因，不占用；返回步骤1。

3a 资源不存在、维护、停用、隔离、实验室关闭或逾期未结束：给出不可用原因，用例结束。

4c 有重叠承诺或他人依赖场地占用：返回时段冲突，不公开人员信息，用例结束。

输入字段：

|字段|含义|类型|条件|范围|来源|校验|隐私|
|---|---|---|---|---|---|---|---|
|资源编号|唯一设备或整间场地标识|业务标识|查询详情/预约/报告时|既有资源；类型由档案决定|目录或受控URL|存在、类型一致；设备标签不因普通编辑变更|资源公共业务属性，不含他人申请|
|开始时间|申请的计划开始|本地日期时刻，含时区解释|时段查询与申请时|Asia/Shanghai；未来14天窗口|用户选择|开始<结束；30分钟粒度；同日；执行时再校验|本人、授权管理员；对外只显示占用区间|
|结束时间|申请的计划结束和应还依据|日期时刻|时段查询与申请时|不超过检查时刻后14天|用户选择|同日，时长≤8小时，位于有效开放区间|同开始时间|
|检索条件|目录搜索字段组|可选文本/标识/枚举|可选|名称/编号、实验室、设备/场地类型|用户|合法字段及对象编号；保留筛选|不包含他人申请条件|

步骤与关键数据：步骤1接收适用输入；步骤4形成或呈现“时段可申请性”。结构：资源编号＋查询时段＋可申请结论＋阻断原因＋查询时点

规则执行位置：BR-03→步骤2；BR-06→步骤3；BR-07→步骤4；BR-39→步骤4

输出与凭据：返回有时间口径的可用结论、阻断原因及重新提交校验提示；不占用资源。

对象状态：Resource,OpeningPeriod,CalendarException,ServicePeriod,Reservation,Loan,RoomUse,UserQualification；参见后置及状态事件字典。

业务规则及权限：BR-03,BR-04,BR-05,BR-06,BR-07,BR-08,BR-29,BR-39,BR-40,BR-44；学生、教师；本人及授权实验室记录

约束：申请默认14天窗口、30分钟粒度、同日≤8小时、每日08:00—20:00；类别未来配额3；设备同时3。批准按当时申请条件，复核与原开始按各自截止。

质量与设计：QR-01,QR-03,QR-08；沿用Django/PostgreSQL与原生小程序；读取时点的派生结果不预留时段；状态提交后新查询按QR-06可见。

验收：AC-05,AC-06,AC-56,AC-57,AC-61

来源与待确认：SRC-A01,SRC-D02,SRC-E01,SRC-A02；真实学校制度与岗位范围待确认；本规约表达已接受课程方案。

描述方法依据：SRC-A03,SRC-A04,SRC-A05；不证明学校实际制度。

## UC-04 提交设备预约

编号版本：SPEC-04 / 2.3；用户目标用例

目标：形成单台或单套设备的明确申请结果与可靠重试凭据

主要执行者：学生、教师；次要参与者：消息服务（业务成功后的投递协作）

涉众利益：申请人需要明确承诺或等待状态和可重试编号；管理员需要受限申请的依据；竞争申请人需要一致的冲突与配额保护。

业务来源：BUC-01；改进步骤：TO-E03,TO-E04,TO-E05,TO-E06,TO-E07

触发：提交设备预约表单

前置条件：受保护请求具有认证身份，调用方以学生或教师申请设备；身份入口不满足由1a拒绝。设备存在性、资格与可用性在流程中重新检查。

成功后置：普通设备为CONFIRMED并有系统决定；受限设备为PENDING并有审核任务。两者占未来设备配额，仅确认状态占时段；保存编号、快照、审计和站内通知/投递任务。

最低保证：业务拒绝不产生新预约或占用；同内容重试返回原编号。外部通知失败不撤销已提交业务；技术失败不留下预约、决定、审计或通知的部分结果。

基本流程：

1. 系统验证当前身份与设备申请角色，接收单一设备和请求标识。

2. 系统核对同标识历史请求，校验资源存在、设备类型、用途、时间格式及先后。

3. 系统检查窗口、粒度、时长、开放、服务、逾期、培训有效期及未来设备配额。

4. 系统对本次承诺重新检查同设备冲突、同时设备上限及固定设备依赖；并发结果以最终一致检查为准。

5. 普通设备形成已确认预约与系统决定；受限设备形成待审核申请。

6. 系统连同规则快照、审计、站内通知及投递任务保存业务结果。

7. 返回编号、状态与下一步条件；本用例结束，不等待人工审批。

备选流程：

2a 同标识同内容重试：返回原编号和当前状态，用例结束；不同内容转2b。

5a 受限设备：PENDING不占资源时段但占未来配额；人工决定由UC-08独立完成，继续步骤6。

7a 后续被驳回或申请人改变计划：分别由UC-08或UC-07产生新事件，不改写本次提交事实。

异常及并发：

1a 未登录或账号/角色失效：转UC-01或拒绝；不建申请，用例结束。

2b 标识复用内容不同、设备不存在、类型错、用途为空、时间无法解析或开始不早于结束：指出字段/原因，不建申请，返回步骤1。

3a 超窗口、非30分钟、超过8小时、跨日、不开放、停用/隔离/维护、资质过期、逾期未还或未来配额已满：拒绝且无新占用，用例结束。

4a 他人确认抢先成功、固定设备依赖冲突、同用户跨资源配额竞争或同时上限失败：拒绝本次提交，不产生半条记录，用例结束。

6a 必要业务保存失败：整体回滚；状态不明时用户用原请求标识重试。

6b 外部消息失败：结果已保存，按UC-23重试，仍返回步骤7。

步骤与关键数据：步骤2接收适用输入；步骤6形成或呈现“预约结果”。结构：预约编号＋申请人＋资源编号＋原计划起止＋用途／人数＋PENDING或CONFIRMED＋规则快照

目标：可靠传递已保存业务的消息并使失败可追踪、可补救

主要执行者：内部事件与调度触发（不是人为虚构的业务执行者）；次要参与者：消息服务（业务成功后的投递协作）

涉众利益：申请人需要结果和失败兜底；管理员需要积压与人工跟进依据；运维人员需要扫描恢复与外部回执边界清楚。

业务来源：BUC-01,BUC-04,BUC-05；改进步骤：TO-E07a,TO-R06,TO-M12

触发：新任务、重试到时、到期或逾期条件满足

成功后置：尝试、发送/重试/失败状态可查；重复扫描不重复生成；最终失败可追加人工联系依据，不改写原业务成功。

3. 投递进程取得租约，调用配置的消息服务。

备选流程：

3a 中断或租约超时：重新领取同任务，使用稳定投递标识；不保证外部提供方无重复，需协议验收。

4a 首次失败后1、5、15分钟重试，最多4次尝试；原业务不变。

5a 人工联系：管理员按范围追加方式和结果审计，不将FAILED伪改成外部送达。

1a 停机后恢复：按当前事实补扫，去重；已开始真实使用不因任务超时伪造归还。

异常及并发：

3b 服务缺配置/失败：记录失败并重试，不以模拟回执代替正式成功。

1b 后台停止：页面可用不代表任务运行；交接仍即时检查禁止条件，恢复后补扫；超调度阈值记运维异常。
