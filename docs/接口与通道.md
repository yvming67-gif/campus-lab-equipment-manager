# 接口与数据通道契约

业务分析采用2.3基线；客户端通道和只读信息组织不改变组织价值、岗位、预约制度或数据库实体。

## 业务职责与客户端分工

|原有职责|客户端承接方式|规约与规则|边界|
|---|---|---|---|
|查询资源和目标时段|网页与小程序保留原查询，并提供可带入申请表的候选时段|UC-02/03；BR-03至BR-09、BR-13、BR-29、BR-39/40|结果是检查时点的快照，不预留资源；原目录可用性与含本人条件的候选预检分别说明|
|查询进度并追加待审核说明|小程序预约详情追加说明，与网页共用`review_note`|UC-06；BR-08/15/26/29/45|仅本人待审核预约可补充；管理员要求补充仍由网页办理，原决定不覆盖|
|审核待审申请|网页提供等待排序、用途摘要及当前检查结果|UC-08；BR-07/08/09/15/26/27|范围、本人回避和最终状态仍由`approve`事务重新核验，小程序没有审批权|
|报告设备或场地异常|小程序文字报告复用原表单和`report_incident`|UC-13；BR-22/26/27/29/37/42|资源、关联归属、发现时间和分级规则沿用原流程；报障不等于已经核实或修复|
|通知查看及标读|明确网页本人批量标读、小程序本人单条或批量标读|UC-22；BR-27/28/29/35/46|阅读状态与外部投递状态分开；这是对既有小程序批量接口的文档补正|

网页继续承接审批、实际交接、异常核实、维修执行与独立验收等管理操作。用户页面展示的负责主体是岗位职责；没有登记的联系人、联系方式或交接地点不补写为学校事实。

## 只读候选时段和审核摘要

小程序资源详情沿用`GET /api/mini/v1/resources/<资源ID>/`。增加`slot_day=YYYY-MM-DD`和`duration_minutes`查询参数时，返回`slot_options`，包含日期、时长、检查时点、候选起止时间、显示标签、是否通过及原因。起止时间包含`Asia/Shanghai`时区偏移；候选选择带入原申请表，正式申请仍走UC-04或UC-05。

候选预检复用`services.validate`及开放日历、固定设备依赖条件。`SlotSnapshot`只为一次候选计算预取事实，没有数据库表或跨请求缓存；写入服务不传这个快照，仍读取执行时事实。候选以人数1进行只读预检，不能据此承诺场地容量已满足实际申请人数。查询结果不包含其他申请人的姓名、用途或材料。

网页审核摘要由`approval_context`返回`checked_at`、`waiting_minutes`、检查项及`can_approve`。每项含名称、当前结论和原因；这只解释当时页面检查结果，不是审批凭据。真正通过或驳回后，仍由既有审批服务生成`ApprovalDecision`、状态变化、审计和通知。

预约详情的`next_step`提供下一步标题、负责岗位、操作提示和交接地点。地点优先读取设备已登记交接地点，再使用所属实验室地点；缺失时明确提示联系管理员。等待审核、暂停交接、已确认、实际使用和终态分别说明，不以计划结束推断实际已经归还或离场。

`GET /api/mini/v1/bookings/<预约ID>/`中，`timeline`和`supplements`分别返回最近100条过程记录与审核沟通，按时间顺序显示；`timeline_total`、`supplements_total`表示总量，`timeline_has_more`、`supplements_has_more`说明是否有更早记录。超出范围时界面提示最近100条并引导至网页预约详情查询完整历史，不把截取结果宣称为全部历史；这只是读取范围，不删除历史记录。

## 小程序补充说明接口

`POST /api/mini/v1/bookings/<预约ID>/supplement/`

|字段|业务含义与格式|校验和可见范围|
|---|---|---|
|`reason`|追加的说明，非空文本，最多1500字符|只追加到本人待审核预约；只向原有有权对象展示|
|`request_key`|客户端首次产生、重试沿用的UUID|与本次操作内容绑定，不是身份凭据；服务端按操作用户隔离|

成功返回预约ID、说明记录ID、当次状态及`replayed`。归属、状态、空内容或失效角色导致拒绝时，不生成合法说明。成功后刷新预约详情读取实际当前状态与追加时间线，不用旧回执覆盖当前界面。

## 小程序文字异常接口

`POST /api/mini/v1/incidents/`

|字段|业务含义与格式|校验和可见范围|
|---|---|---|
|`resource_id`|异常资源的正整数ID|资源须存在；目录可见不赋予管理权|
|`reservation`|可选的关联预约ID|只能关联本人预约，且预约资源必须与报告资源一致|
|`kind`|`DAMAGE`、`MISSING`或`FAULT`|沿用损坏、缺件、运行异常三个原有类型，不新增安全类型枚举|
|`description`|现象说明，非空，最多2000字符|保存可核查事实，不由客户端自动定责或判赔|
|`occurred_at`|发现时刻，日期时间|不能晚于系统当前时刻；与报告保存时刻分别记录|
|`request_key`|首次提交生成、重试沿用的UUID|按同一操作用户和规范化内容去重|

成功返回异常ID、编号、核实状态、`blocks_service`、资源和关联预约标识。普通无关联报告先待核实；关联本人使用中报告按既有服务分级处理。核实状态与是否阻断不是同一字段，不能把所有报障画成自动确认或自动隔离。紧急现场情况应联系现场管理人员，不能把提交文字报告当成已经有人即时响应。

当前不增加小程序附件上传或证据读取接口。需要照片或PDF时，仍按UC-25的网页受控流程和对象权限办理，不把原始存储地址当成公开访问凭证。

## 超时后的结果核对

接口：`GET /api/mini/v1/receipts/<请求UUID>/`。返回`found`、最小结果和提示。未找到回执不证明提交失败；客户端保留原请求标识及内容，可先核对再用同一标识、同一内容重试。同一标识复用到不同内容或不同动作时拒绝。

补充说明与异常报告的传输回执复用既有`AuditEvent`：

|既有字段|用途|约束|
|---|---|---|
|`actor`|实际操作用户|请求通过有效小程序会话认证，不能由客户端指定他人|
|`entity_type`、`entity_id`|关联操作用户这个既有对象|当前代码由`s.audit(current,current,...)`生成`user`逻辑引用，不存在新增的`mini_request`实体|
|`action`|`MINI_ACTION_RECEIPT`|显示为小程序操作回执，不代替原补充说明或异常业务审计|
|`dedupe_key`|操作用户与请求UUID组成的稳定键|沿用原有唯一约束；两个动作共用用户内键空间，防止跨动作误复用|
|`new_state`|规范化内容摘要和最小结果|不保存登录密码或身份令牌；原业务内容仍在对应业务实体中|

用户行锁、业务服务、领域审计、站内通知、外部投递任务和传输回执在同一事务中完成。必要保存失败回滚；外部投递仍在业务提交后独立处理。回执仅证明原操作当时的结果，之后预约取消、异常处置或角色变化要通过当前对象重新查询。

## 分析模型和验收边界

当前仍为27项系统用例、46条业务规则、DC-01运行恢复约束、11项质量需求、66项既有验收场景，以及36个领域实体、289字段、61条物理外键。接口和`SlotSnapshot`不是新增组织服务或持久实体；无须为页面变化重画ERD。现有图中师生参与者、UC-03/06/13职责仍能承接新通道。

本契约说明字段、职责和实现承接，不单独证明测试通过。网页、原生容器、手机与平台发布分别记录，见[验证说明](验证说明.md)。
