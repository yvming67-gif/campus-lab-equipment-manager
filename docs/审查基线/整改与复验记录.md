# 整改与复验记录

本轮不修改业务代码，全部问题状态仍为待整改或待评估。下列顺序表示建议，不是校方批准的排期。独立的业务选择应先确认，再修改规则；保持单体架构和现有数据库可以完成首轮改进。

## 试点前

先处理AUD-0001撤权交接，再校准故障/资格变更影响通知、前人逾期协调和风险升级政策。修复已确认的列表、查询、500、权限链接、参数文案、审计旧值以及小程序异步和断网恢复。保留原业务事实和审计，不用直接改数据库补过。

先验证学校身份、至少一种真实通知渠道及资源物理独立性；建立管理员备岗、维修重派和责任争议的最小流程。部署采取学校能维护的单实例服务、HTTPS和最小数据库账号，验证异地副本与源库不可用时的恢复手册。当前微信开发者工具导入和主要流程验收是小程序试点门槛；真机发布单独验收。

## 试点期间

选少量符合日间短借的资源和管理员范围，保留并行人工核对凭据。采集真实查询、确认、到场等待和维护同步基线；记录爽约原因、前人延误、故障影响和争议。按热点目录/报表/跨端比例补负载样本，观察任务心跳、投递积压、备份年龄及磁盘使用。优先修复本轮轻微标签、导航、文案和文档问题，避免长期积累。

## 扩大使用范围后

只有学校制度和试点证据需要时，增加节假日例外、长期实验、教学优先、固定设备关联和更丰富报表；不把门禁、财务赔偿、采购和全校排课自动列为必须开发内容。按测得瓶颈做批量查询或索引优化，再评估进一步扩容。持续演练恢复和升级回滚，完善个人资料与证据保留制度；跨校或多实例不是当前必需目标。
