# 审查概览

审查日期：2026-10-20。对象：[yvming67-gif/campus-lab-equipment-manager](https://github.com/yvming67-gif/campus-lab-equipment-manager)。固定分支 main，提交 [`453e45e7f75b6be1e71a90b846b669cfd5cef026`](https://github.com/yvming67-gif/campus-lab-equipment-manager/tree/453e45e7f75b6be1e71a90b846b669cfd5cef026)。GitHub只读API与本地HEAD一致，原项目工作区开始与结束均干净。本轮没有修改业务代码、提交Git或更新GitHub。

## 总体判断

**这是具有真实事务、权限及维护闭环的课程演示系统，常规本地流程有可运行证据；目前不宜直接作为真实校园的独立工作系统上线。** 它具有继续建设的基础，主要差距同时来自实现反例与尚未完成的业务、身份和运行适配，不能简单归因于架构不够复杂。

课程定位下，112项既有后端测试、21项客户端测试、11项启动器测试通过，但额外反例确认了撤权后仍可现场开始、查询提示与规则不一致、列表截断、异常链接404、小程序断网恢复和异步覆盖等缺陷。**“已有测试通过”不能替代这些缺陷的整改，也不等于本轮观察脚本中的所有业务预期都通过。** 主流程可演示，不代表边界可靠性已经合格。

真实试点应先明确可独立取放的资源清单、学校身份与资格回收、管理备岗和争议责任；修复已确认缺陷，补上受影响预约协调、真实消息、最低限度的生产托管和可执行灾后恢复。可先选少量日间可移动设备与一两间实验室试点；没有证据要求拆成微服务、引入集群或更换Django/PostgreSQL。

## 值得保留的设计

- 设备和场地共用预约规则，又分别保存Loan/ReturnRecord与RoomUse事实，避免审批通过被当作实物交接完成。前一借出未归还时确实阻止下一借出，没有为了“流转顺利”伪记归还。
- 申请人/资源锁、批准前复核及PostgreSQL条件区间排斥共同工作。本轮独立双用户、双管理员竞争均最多一份确认；既有100组竞争、跨资源配额及直接数据库排斥断言也通过。证据限于这些场景，未断言所有并发都已证明。
- 网页与小程序调用同一业务服务；小程序不信任客户端传来的申请人或状态，个人对象越权与跨实验室越权检查在已测入口正确拒绝。
- 异常、工单、技师提交和管理员验收相互区分；验收不通过保持维护中，其他异常/手工限制不会因某一工单关闭而被一并清除。
- 业务、审计、站内通知在同一事务内保存，模拟外部投递另行重试和去重；4次失败未回滚预约，任务恢复补扫没有重复失效。现有投递骨架可继续用于真实渠道。
- 审计触发器在普通DML下拒绝改删；备份演练及本轮全表内容摘要核对通过。需同时保留超级用户边界、同盘备份和离线恢复流程等限制。
- 报告诚实标注情景假设和初步目标；计划与实际利用率分列。ERD有字段和关系索引，未把逻辑审计引用伪画为物理外键。它们适合作为需求基线，结构检查不替代行为验收。

## 待确认事项

1. 真实首批使用者、设备/场地数量、上课高峰和维护人员值守能力；哪些设备可独立外借、从哪里取还。
2. 场地占用/关闭与固定设备、安全设施之间的真实依赖；房间关闭是否必须联动设备。
3. 普通/高价值/危险分级的审批依据、培训有效期、等级提高是否追溯未开始预约，以及撤资格后的通知和处置责任。
4. 低门槛报障是否立即隔离全体资源；谁核实、多久响应，误报如何处理。
5. 教学优先、考试周、节假日和长期科研是否在试点内；14天、8小时、配额3项与日间不跨日是否适用。
6. 前序逾期造成守约者等待、临时故障、审批缺席和维修离岗时，谁可以协调和变更，如何不覆盖原始责任。
7. 双方交接确认、损坏争议、追加证据与中心复核制度；财务赔偿可继续留在系统外。
8. 学校认证、通知渠道、HTTPS与部署责任、数据库运维权限、RPO/RTO、异地备份保留和个人资料生命周期。

这些问题会改变上线范围和优先级，不能由本轮代码审查替学校编造答案。结论受已覆盖路径和环境约束，**没有宣称发现全部潜在缺陷**。
